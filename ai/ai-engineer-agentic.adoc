=== Day 2 - What Is an AI Agent? Definitions, Workflows vs Agents Explained

_Theory_

Is there a well understood and definition of Agent?

No.

AI Agent could be anything that you wanted it to be. But there are a few sensible
definitions

- Sam Altman - "AI systems that can do work for you independently". This is gooey,
GPT Agent. Operator. The idea is to give a task, and then that agent goes and
takes actions. Something goes off, and does work for you.
- Early 2025 consensus - AI systems where an LLM controls the workflow
	- Rather than coding, you prompt an LLM, and tell him "what can I do? A, B
	or C?" - The LLM chooses
	- The idea is to interpret the output and define the workflow
	- **An LLM is just a type of data science model, all it can do is take input,
	which breaks into tokens, and it outputs the most likely tokens that follow
	that sequence**
		- We can write code that interprets the output and react to it. The LLM
		generates tokens, and we are controlling the workflow. **WE CONTROL**
			- The agent is our code, that interprets the output tokens of an LLM
- Current prevailing view - An LLM with Tools in a Loop to achieve a goal
	- This is the definition everyone has signed up for
	- n8n => An LLM with tools, in a loop, to achieve a goal. The best demo ever
	to demonstrate the definition
		- We wrap the output, we interpret it, and our code, our Agent, turns the
		vanilla LLM into an Agentic tool.

**Agentic Systems**

- Anthropic posted an article that lays out a lot of the terminology in the area.

There are two types of Agentic Systems:

- Workflows
- Agents

_Terminology is loose_. It's one way to think about it.

**Workflows:** Are systems where LLMs and tools are orchestrated through predefined
code paths. (It's not fully open. It doesn't mean one LLM doesn't decide where
the execution goes. But there's a relatively specific path, and you know how to
test all those variations within the path).

Think of the "Deep" feature. How ChatGPT asks, and takes series of steps in a
pre-defined code-path. That can be a workflow.

**Agents:** Are dynamic systems where LLMs direct their own processes and tool
usage, maintaining control over how they accomplish tasks.

Think of an agent that works independently on its own, "brings up programs, browsers,
and does its own things".

Coding Agents => Feel super dynamic, and that do everything on their own.

[IMPORTANT]
====
There can be gray areas within these definitions. Sometimes, you can add guardrails
to an agent, and make a strict pigeonhole. Anthropic => Calls all of these systems
**Agentic Systems**
====

Real, production systems => **People lean into workflows**. You want something to
be repeatable, testable, and with a pre-defined code-path. Yes, the LLM can take
some decisions here and there, but in the end, you want robustness.

=== Agentic AI Design Patterns: Chaining, Routing, Orchestrator

"Building effective Agentic Agents"

This article introduced some patterns when building agentic systems. Now, these 3
patterns are meant to be thought provoking, to give you base ideas that you can
start with and go off when solving problems. They are not set in stone, and should
not be taken as gospel.

- Software Engineering background => Is more mature, and there are design patterns
that are more "set in stone". However, the patterns in this Agentic space are more
loose. These are not rigid patterns.

They are just ideas for interesting approaches for actual production systems.

==== Prompt Chaining

Decompose into fixed sub-tasks

. There's input
. LLM1 call
. Gate (this represents a decision in code)
. LLM2 call
. LLM3 call
. Out

This is the first pattern. Prompt chaining often forms a building block of a
bigger pattern.

==== Routing

Direct an input into a specialized sub-task, ensuring separation of concerns

. Input
. LLM Router
. LLM1
. LLM2
. LLM3
. Out

This is another prompt that is sent to an LLM that is best prepared for a specific
type of question. **Separation of concerns**, so that you send LLM calls to specialized
LLM models (which gives the best performance)

_How do I know I need to breakdown a problem?_ => Wait a bit.

==== Parallelization

Breaking down tasks and running multiple subtasks concurrently.

. IN
. Coordinator
. LLM1
. LLM2
. LLM3
. Aggregator
. Out

==== Orchestrator-Worker

Complex tasks are broken down dynamically and combined

. IN
. Orchestrator
. LLM1
. LLM2
. LLM3
. Synthesizer
. OUT

The difference is that the orchestrator and Synthesizer are LLMs themselves, they
choose how to breakdown the input into other pieces (that other LLMs respond),
and then the last LLM decides how to put together all the outputs.

These patterns are very common. And seen in many shapes and forms across multiple
agentic systems. The idea is to treat some form of input, pass it down to another
LLM, and keep chaining things.

**Pre-defined code-path**

==== Evaluator-Optimizer

LLM output is validated by another

. IN
. LLM Generator - Solution or Rejected with feedback
. LLM Evaluator - Accepted
. OUT

The idea is to stay in a loop until an LLM accepts the result of another LLM and
then outputs a solution.

**By contrast agents:**

. Open-ended
. Feedback loops
. No fixed path

HUMAN => LLM Call - Action/Feedback (On Environment) - Stop

As you can see, an agent is just an LLM call that runs on a loop, and keeps going
until it decides it's reached its goal.

_Don't get hung-up on the names, the idea is to understand the main idea_

=== Agentic AI Risks, Guardrails, Evals and Traps to Avoid

- One of the great benefits of Agentic AI is for fluent and flexible solutions that
solve things in different ways
	- But that's its weakness as well - **Unpredictable path**, **Unpredictable output**,
	**Unpredictable costs**

But you can mitigate this unpredictability.

- Monitor => (Observability, Evals). You need to have the right kind of information,
traces that shows you what is happening with your agent calls.

Eval => End commercial goal. How many new customers, leads do I get?
Eval => How many revenue do I get based on sales made by my agent?

This is how you truly evaluate if your agentic framework is actually worth it.

**Use an LLM whether an output is good or not** => _Evaluator-Optimizer pattern_.
You can use that `LLM as a judge` to evaluate your business itself.

- Guardrails => Ensures your agents behave safely, consistently, and within your
intended boundaries
	- It's just tests that you add, the LLM generates an output, you can check it,
	make sure you are happy with that test. This is another way to mitigate Agentic
	Solutions

==== Traps

**The First Agent Trap**

"I need an Agent for my business" - "Ok - and what business problem is that solving"
- "I want an Strategy Agent to give me advice for my org" - "OK, right, and... what...
_business problem_ is that solving"

**Always bring back to the commercial problem that is to be solved**

- Maybe this involves LLM Agents, **maybe not**

Only if you have a problem to be solved, only then you can measure if you solved
said problem with the LLM Agent. **Don't be solution-oriented, start from the
business problem**

_Sometimes you have to change the conversation to a business problem_

**LLMs are good at generating content** => They are trained to generate content that
is believable. But to check if that output is actually good, to measure the business
outcome, and iterating until the business problem is solved. **You need to know how
to measure that a problem is solved**

An Agent in a loop is constantly driven to improve the metric of solving the problem.

**The Second Agent Trap**

Anthropomorphizing

- A common red flag: "Agent Architectures" that assign human-like responsibilities
to Agents

Trading Manager Agent - Market Research Agent - Trader Agent - Risk Manager Agent

So you draw boxes and give names to agents with roles as if they were humans.

**This is bad**. Agents are not people, they are token generation models.

_The right approach:_

**Start simple**

Start with **One LLM**. One prompt, one objective. And then **you measure performance
against a business objective**

Add Agents because it improves performance => Do the scaling in a measurable way.
As part of the experiments growing the architecture intentionally is what should
drive you to make it bigger.

**Do not think as humans would do something**. Measure outputs, and start simple
_always_.

==== Takeaways

- Build Agent systems to solve problems in a measurable way
	- Pushback, challenge, and get to a business problem.
- Decide your Agent Architecture based on performance
- LLMs generate plausible outputs, not necessarily accurate outputs
	- Aligning the outputs with business results? That's your job
	- The AI Engineers align the token output with business expectations

**Hallucination** => This is not a move available for AI Engineers. That is an
excuse for AI users. The idea to take the output of an LLM, and validate it,
test it. **THAT'S YOUR JOB**

````
    response = openai.chat.completions.create(model="gpt-5.4-mini", messages=messages, tools=tools)
````

==== The Short Version

If you work with async Python.

- All methods and functions start `async`. Everything runs at the same time.
Everything starts with the `async` and you have to use `await` before calling
a function.

```
async def do_some_processing():
	# Do some work
	return "done!"

result = await do_some_processing()
```

==== The Longer Version

It's common in computing to do several things in parallel. And it's particularly
true for AI Agents. And that is because you are waiting for an LLM to respond,
that LLM is running in another person's computer.

So instead of waiting there, you should parallelize -> Multi Threading, Multi
Processing. That is a better usage of resources.

But this incurs in some issues => Concurrency. You should write code that operates
on multiple threads, without harming itself or state.

`asyncio` provides a lightweight alternative to threading or multiprocessing.

You are explicitly explaining how the code should cooperate.

Functions defined with `async def` are called `coroutines` - they're special functions
that can be paused and resumed.

If you define a coroutine, and then you call it, that doesn't run anything. Nothing
gets called, it returns a `coroutine` object that represents that task that will
run the function.

**How does the coroutine runs?** - The `await` prefix has to be applied. This will
schedule the `coroutine`. **Event loop:** This is like a small agent, that runs
all the courutines that have been added for running. It's a like an agent that
runs in a queue tasks that are going to be run.

`await` => I want to schedule this coroutine to write in the future.

While a coroutine is waiting (e.g., for I/O), the `event loop` can run other courutines.

It's not like multi threading or multi processing. You are explicitly programming
what's gonna happen. Only one coroutine runs at a time.

_It's a brute force approach_

- This is called **Cooperative Multi Tasking**
- Pre-emptive multitasking => That's multithreading and so on.

[source, python]
----
async def do_some_processing() -> str:
	# Do some work
	return "done!"

# running the function returns a coroutine
my_coroutine = do_some_processing()

my_result = await my_coroutine
----
However, if you think that simply creating multiple objects and then try to await
them all at once, this won't parallelize execution. **It will run serialized**.

That's why we need another construct that can parallelize the coroutine execution:

```
results = await asyncio.gather(
	do_some_processing(),
	do_other_processing(),
	do_yet_more_processing()
)
```
These will all run _apparently concurrently_, however it will still run in sequences.
But because we are sending to LLMs, we will at the very least win some time and
processing by blocking our threads through I/O from the processing on the LLMs'
servers.

You are I/O bound => Waiting for the network, so that you chop-up your sessions.
Threads are not a limiting factor here.
If you are CPU bound => Rarely happens when working with LLMs. But in there you
will have to parallelize with concurrency in mind. The threads of your computer
can also be a limiting factor.

_Only one thing is running at a time_, no concurrent issues. So don't worry.

with other agents. He orchestrates the workflow.

docs of OpenAI)

**Structured Outputs:** The LLM should not respond just with text, it should respond
with a JSON, that should conform to some sort of spec that you craft. And with that
output, you determine what happens next. It's a much more organized way for you to
write code that looks at the structured output and take decisions.

_By experience, the instructor says that in production, you prefer code orchestration,
so that's more usage in the industry_

=== Orchestrate Agents as Tools with a Sales Manager Agent

`Tools` => The more recommended approach. So that one Agent chooses to invoke another
Agent (through a tool). This is really easy to do within the same `Runner.run`
execution. This works perfectly when you have Agent A => That sends to Agent B
something => Agent A expects a response back.

`Handoffs` => Variation on tools, but it's a bit unreliable.

```
description = "Use this tool to write a sales email. In the input, just instruct it to write a sales email."
```

You can literally take an already created agent, and use `as_tool`. This will autogenerate

was applied this on.

With this concept in mind, we will turn all our agents into tools:

```

tool3 = sales_agent3.as_tool(tool_name="sales_email_writer_3", tool_description=description)

tools
```
We are shoving in the sales agent tools, and the send email tool.

=== Orchestrate Agents with Handoffs in the OpenAI Agents SDK

Handoffs are not used as other Frameworks. Prompts are baked into a Framework, that
is Framework Voodoo. And Handoffs are doing just that.

An agent can delegate to another agent, parsing control, in a way we don't expect.

```

instructions = """
You are a Sales Manager at ComplAI. You get your sales team to draft emails, then send them all to a sales picker.
"""

task = """
Follow these steps:

1. Generate Drafts: Use each of the three sales_email_writer tools to generate different email drafts.
Just instruct each to write a sales email; no further details are needed.
Do not proceed until all three drafts are ready, one from each tool.
 
2. Handoff to the sales sender to choose and send the best email.
"""

tools = [tool1, tool2, tool3]
handoffs = [sales_sender]

sales_manager = Agent(name="Sales Manager", instructions=instructions, tools=tools, handoffs=handoffs, model=MODEL_NAME)
```
The idea is that we setup the tools, and we then setup a handoff, which is another
agent.

If we visualize the diagram of the setup with Handoffs, we are baking in that
there's a Sales Manager that send an instruction to a Sales Sender.

Still, the running is one sole run:

```
with trace("Sales manager"):
    result = await Runner.run(sales_manager, task)
```

The handoff => Is when the sales manager passes down the execution to the sales
sender agent. So in short, you are passing down the execution power to further
agents down the chain.

- Spinning up multiple agents
- Have another agent evaluates the other agents' outputs
- Changing an agent into a tool
- Handoffs so that the agent will decide to pass control over to based on the way
the instructions have been laid out

_IDEA:_ You could even have another LLM that refines the email that was selected,
before sending it.

=== Structured Outputs with Pydantic in the OpenAI Agents SDK

LLMs produce language. That's what they do: _Generate tokens, the most likely sequence
to follow an input_).

However, if we prompt it correctly, it can also generate JSON.

_It's all about trickery with LLMs_. We make good and creative prompts, to get
around problems, and reach the end goal by talking to an LLM, and the LLM responding
with something we can structurize.

There's a popular framework (library) to define a JSON schema that can then be
turned into an object: `Pydantic`, which has a really simple and intuitive API.

[source, python]
----
class EmailReview(BaseModel): <.>
    is_professional: bool = Field(description="Whether the email is professional and appropriate") <.>
    number_of_sentences: int = Field(description="The number of sentences in the body of the email, not including the greeting and signature")
    contains_placeholders: bool = Field(description="Whether the email contains placeholders for personalization")
----
<.> You essentially declare a class that needs to inherit from `BaseModel`
<.> And then you declare a field, with its type and then metadata that helps describe
the field. **This is really important for the LLM to know how to fill the field**
There's one thing about structured outputs that the LLM adds as a safeguard. And
that is "constrained decoding". Basically, an LLM could be generating wrong JSON
output and break our code. However, under the hood it really makes sure (almost certain)
that when selecting the next token, they zero-out the tokens that would break
a spec you provide. _This is how LLMs are very good at generating a JSON that
conforms to a schema_.

**Not all LLMs support structured outputs**

[IMPORTANT]
====
Keep your JSON schema relatively simple.
====

It's a lot to ask, for LLMs to work with highly nested and complex JSON objects.
So try to reduce risk there.

You can see the janky JSON of a schema: `EmailReview.model_json_schema()`

**Structured Outputs is scaffolding**

Now let's run a small example:

```
email = """
Hi [first_name],

I'm hitting you up to see if you'd like to buy our product. It's really great. You'll miss out if you don't buy it.

Laters.

Ed
"""

checker = Agent(name="Checker", instructions="You review potential sales emails", model="gpt-5.4-mini", output_type=EmailReview)
result = await Runner.run(checker, email)

review = result.final_output
review

review.is_professional
```

Look at this. We aren't really asking the LLM about its output, we are not really
telling it much, as far as the user prompt goes, or event the system prompt.

However, based on the structured output, and the user input it responds with JSON,
yet that JSON is filled in with information that is extrapolated from the prompt
and some sort of "evaluation"

Why do we know this, because the result can literally look like this:

`EmailReview(is_professional=False, number_of_sentences=3, contains_placeholders=True)`

The OpenAI Agents SDK library does a lot in the background, because it leverages
JSON the Pydantic object and outputs directly the object instance.

==== Guardrails

Something really important as a concept is guardrails. **You can write guardrails
yourself**. However the SDK has an API for Guardrails, really opinionated and with
multiple constructs.

It's really set in its ways, so you can't migrate easily to other framework, it
has a lot of Voodoo Framework, and updates run risks of breaking your solutions.

_The preferred approach will always be to write your own code for guardrails_

There are three types of guardrails:

- Input guardrails => This runs only for the first agent on the chain
- Output guardrails => This runs only on the last agent's output
- Tool guardrails => Runs on every custom function-tool, before execution and
after execution

**Tripwire:** If this is triggered, then an exception is thrown because an agent
hit the guardrail.

_Why are Guardrails associated with an Agent?_ _Shouldn't it be in the `Runner.run`?_

The real problem: Guardrails are just tests and controls => You should be able to
write them anywhere you want. But OpenAI thinks otherwise. They want to attach
the Guardrail to an agent.

- `Parallel execution` => This is run like this by default, but there might be
scenarios in which multiple LLMs were triggered, yet one that had the tripwire
later triggered makes the whole execution fall, but you already wasted LLM calls.
So _be careful around this_

=== Build Guardrails for AI Agents Plus Sandboxes and MCP

Guardrails are themselves making an LLM call. Because they should make a judgement.

[source, python]
----
@output_guardrail
async def email_guardrail(ctx, agent, message): <.>
    result = await Runner.run(checker, message, context=ctx.context) <.>
    review = result.final_output
    is_problem = review.contains_placeholders or not review.is_professional <.>
    return GuardrailFunctionOutput(output_info={"review": review},tripwire_triggered=is_problem) <.>
----
<.> A guardrail basically receives a context, an agent and a message. The context
is an extra object that might be useful in some use cases that require further
metadata and info, the `agent` is some specific agent to which you can apply a
guardrail, you could re-use the guardrail with multiple things, however we are
going to use just one. And lastly the message we will analyze and make the guardrail
for.
<.> We will run the agent that we used to check if an email has problems and
so on, on top of the prompt, and lastly we will extend the context.
<.> We are going to check two properties that come from the structured output to
deem in a boolean variable whether the guardrail should trigger the tripwire
<.> And we have to return a `GuardrailFunctionOutput`, we will add a `review` property
to an object, and then based on what we find (if there is a problem or no) we will
also state if the tripwire was triggered.

Let's willfully try to make an agent that will write a bad sales email:

```
cowboy_instructions = instructions + "\nSpeak like a cowboy"

sales_agent_cowboy = Agent(name="Cowboy", instructions=cowboy_instructions, model=gemini_model, output_guardrails=[email_guardrail])
```
Look how we are applying a guardrail through `output_guardrails.`

```
result = await Runner.run(sales_agent_cowboy, "Write a cold sales email")
result.final_output
```
Immediately the run would throw an exception, because of the guardrail.

And that is because the cowboy email was deemed as innapropriate.

The trace even shows a specific item when it comes to a tripwire that was triggered.

**On the other hand, you can write guardrails yourself:**

```

result = await Runner.run(simple_cowboy, "Write a cold sales email")
email = result.final_output

if not review.is_professional or review.contains_placeholders:
    print("The email is not professional or has placeholders and will not be sent")
else:
    print("Email is good")
```

That is all that we are doing in our guardrail => Keep it simple. Guardrails can
be implemented by simple calls to `Runner.run`. And sometimes you will have to
duplicate code. _But that's a good tradeoff instead of framework voodoo_. Run
the checks you want to do **when you want to do them**

_Simple is better_

And that is because it will work within any agent framework, you won't tie to
the Framework's flavor of Guardrails.

==== MCP Teaser

To start talking to an MCP Server you can import from a module and leverage it:

```
from agents.mcp import MCPServerStreamableHttp

task = """
In the new SandboxAgents feature in the OpenAI Agents SDK as of May 2026, what is the role of the Manifest object?
Always be accurate. If you don't know the answer, say so.
"""

params = {"url": "https://mcp.context7.com/mcp", "timeout": 60}


async with MCPServerStreamableHttp(name="Context7", params=params) as server:
    agent = Agent(name="Expert", instructions="Use Context7 to answer the question", mcp_servers=[server], model="gpt-4o-mini")
    result = await Runner.run(agent, task)

print(result.final_output)
```
Look how and MCP enables an agent to use tools that someone else wrote. You don't
have to write tools yourself.

that gives info about APIs to an LLM.

And so, if we load an agent with the mcp server `mcp_servers=[server]`. And ask
the same question, we will actually get a proper answer. All because the agent
which had a cutoff training date before the feature was a thing, leveraged an
extra tool and had the ability now to answer the question.

_We could write a tool ourselves, add docstrings, and so on_. However with an
MCP, you would just make a call to the server. And then the LLM would take care
